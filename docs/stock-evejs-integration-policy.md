# Stock EveJS integration policy

Web Companion targets the published stock EveJS interfaces and original game protocol. The clean stock source is authoritative. Do not change EveJS core, add private runtime endpoints, install WC authority patches, or move those patches into a mod. A local `-test` runtime or patched server is not evidence of upstream support. Unsupported authority must produce a deliberate refusal or UNKNOWN observation, never fabricated readiness.

Discuss any proposed server-side extension with Farmer, Tokeiito or the relevant upstream contributor before implementation. Prefer real-client and existing stock semantics. A proper mod may be considered only after explicit upstream agreement; that agreement must establish its optional feature contract rather than making it a hidden dependency of generic WC functionality.

Generic browser and hosted selection use stock `/session/select`, which dispatches `charService.SelectCharacterID([characterID, null, true])`. Stock duplicate-login behavior depends on `network.loginTakeoverEnabled` (default true). WC refuses known foreign WC owners, exact operation reservations, observed external online pilots and unresolved custody. Those checks cannot atomically fence an external login after an offline observation. A concurrent external login follows the server's ordinary retail takeover/refusal policy, including failed-handoff restoration. WC never claims that its in-memory reservation protects an external game session. The original game-port protocol reaches the same server handler and does not offer a stronger free-only command.

Browser handles are web gateway leases; they cannot be relabelled or transferred as a new hosted identity. Caller-held handoff runs custody/drone checks, releases its exact handle, transfers its exact private WC reservation to the new private claim, then selects normally. Both character and caller-session reservation maps must agree; stale capabilities and callbacks cannot affect a newer generation.

Training account/character creation, roster, corporation fitting qualification and offline queue review/apply use stock interfaces. Optional corporation onboarding uses dedicated stock sessions and ordinary retail selection semantics. It refuses observed owners and WC reservations, retains non-CEO checks, and cleans only exact handles. Stock release acknowledges `released` and `characterID`; a separate exact character-status read proves offline. Uncertain cleanup remains RECOVERY. Direct skill purchase and its automatic funding are unavailable through the stock web gateway; original `skillMgr` supports purchase, but no reviewed web-compatible acquisition lifecycle is supplied here.

Selected NPC-station Ready Fit, Provision Ship and Replenish retain their stock inventory, fitting, generation, source-access and custody proofs. Standalone Provisioning Center Apply and Training Provision Equipment use explicit bounded stock selected maintenance control. Opening, refreshing and reviewing these pages selects nobody: account preflight pins intent and saved definitions while physical equipment, source stock and Take authority remain UNKNOWN. Apply reserves exact WC character/session identities, selects normally, captures its first authoritative selected baseline, invokes the same selected ship provisioning engine, verifies and releases its exact handle, then separately proves offline. This is ordinary retail acquisition, with the same residual external-login race as hosted Start; it is not atomic free-only acquisition. Historical and interrupted invocation records remain readable. Recovery releases an existing exact in-memory handle or observes offline status, never reacquires or resends an interrupted mutation. Pending custody and unproved release remain fenced. See [the maintenance lifecycle](stock-hosted-maintenance.md).

MCC planning accepts configuration and saved-definition intent only. Equipment, supply stock and Take authority remain UNKNOWN/PENDING until the exact final hosted owner reads them. A version-2 checkpoint saves its first selected physical baseline before mutation, pins exact definition/source/quantities, and uses the existing shared replenishment journal. It never refreshes that baseline on recovery. Verified earlier sibling movements are already represented by a later baseline; only subsequent same-run, same-physical-source custody adjusts it. Baseline capture refuses unsettled sibling custody and retries its read once if represented WC journal evidence changes during that read. This does not fence external inventory changes; existing strict review/readback checks still apply. Persisted version-1 pins retain their original strict comparison. Productive MAIN waits for the existing aggregate readiness barrier. Defender verifies skills, weapon classification and ammunition before transfer and again before MAIN.

Stock stateless account-owned structure search can enumerate accessible structures: `[0]` falls back to system zero in that stateless context, and the stock directory applies no system filter. Held `[0]` scopes to the held session's current system. Docking access authorizes search/travel; it does not prove all service rights. Service-gated structure inventory/fitting/office actions refuse explicitly because stock web allowlist lacks authoritative services and office rental. Native `structureSettings.CharacterGetServices` and `officeManager.RentOffice` exist, but a safe adapter for held web sessions is an upstream design question. NPC station paths remain supported.

Mining reach, Core/fuel, burst and compression fields missing from stock snapshots remain UNKNOWN and follow existing fail-closed controllers. No runtime projection is installed to manufacture them. Ordinary supported movement/combat remains on the existing protocol; authored entry-room, gated DED/multi-room/signature and mission-combat authority must remain unavailable where stock cannot prove it. This change imports no Combat Operations worktree.

Patch installers, helpers and implementation tests have been retired from the current tree. Git history preserves their provenance, not deployment authorization. `build-bridge-contract --write` updates WC only and treats EveJS as read-only. Tests must cover public hosted Start/Stop without Factory methods, selected preparation, exact ownership/restoration and deliberate unsupported responses. Live QA on a locally extended server alone is never stock compatibility evidence.
