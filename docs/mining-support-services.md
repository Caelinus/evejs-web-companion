# Mining Support contracts and current implementation

`AppFlow.readMiningSupportServices()` enriches Phase 1A capabilities with the latest successful, same-ship space snapshot. It performs no IO, actions, fitting loads or caching. Callers refresh through the existing `loadSpaceSnapshot()` reader. A failed read, ship change, absent field or unreadable observation grants no service facts. The server sample timestamp is retained; no freshness timer or recipient-expiry claim is introduced.

Each fitted Mining Foreman Burst has a separate active/inactive/unknown service state. Active facts preserve the runtime module item ID and type, effect identity, charge type, computed burst range, cycle and buff durations, and buff-collection IDs/values. These are the activation snapshot produced by `commandBurstRuntime`, not a new calculation. The current runtime effect state does not retain the consumed charge item's ID, so the service's charge item ID remains null; the capability snapshot independently retains the latest observed loaded charge.

Compression service records preserve facility ship/pilot/owner identity, self/external origin, active/inactive/unknown state, active compressor identities when available, and each exact `{typeListID, rangeMeters}` association from `compressionFacilityTypelists`. External does not prove fleet membership or access. Typelist IDs are retained without guessing ore/ice/gas labels. The authority currently merges compressors covering the same typelist; module identities are therefore listed independently without inventing a module-to-pair association. The old `compressionFacility.rangeMeters` maximum remains for compatibility with existing WC consumers and is never used to construct these new service facts.

Each fitted Industrial Core has an independent inactive/active/deactivation-pending/unknown observation, matched by fitted item and type identity. Current effect identity, start, cycle duration, next boundary, stop request and scheduled deactivation timestamps are preserved. A passed boundary never proves shutdown while the authoritative active effect remains. Only actual effect-map absence proves current inactivity; no completed shutdown timestamp or reason is fabricated.

Movement and warp restrictions are separate verdicts from `shipActionRestrictions.isShipMovementLockedByRuntime` and `isShipWarpDisabledByRuntime`, evaluated using the scene simulation-clock reader used by the handlers. Zero is a valid clock reading; unavailable simulation time grants no verdict. These are the same runtime gates enforced by pilot movement/warp handlers, and they can disagree. The scope is explicitly `runtime-action-restrictions`: unrestricted is not a guarantee that target validity, current warp/landing, docking, tackle, destination or other action preconditions pass. Known restricting module/effect identities accompany the verdict; non-module restrictions may have no effect attribution. The warp gate's existing `SHIP_IMMOBILE` code is retained; sublight handlers do not supply a code. An unreadable gate stays unknown.

Core fuel requirements come from the existing runtime module authority. Fuel name is resolved only from WC's existing names cache. While active, `effectivePerActivation` is copied from the effect's already-rounded `fuelPerActivation`, the exact value passed to the continuing-cycle consumer. While inactive it remains null: base consumption is not presented as an effective activation quote. Eligible inventory stacks, location/flag identities and available quantity use `sharedFuelRuntime.getFuelStacksForShipStorage` / `getFuelQuantityFromStacks` and `fuelBayInventory.getFuelStorageFlagsForType`. No additional WC inventory loader, fuel bay router, rounding or skill arithmetic is introduced. A readable empty inventory is zero; failed or identity-unscoped inventory reads are unknown.

The decoder retains supplied activation failure and stop codes and normalizes `NO_FUEL` / `fuel` without deriving them from inventory quantity or inactivity. Current EveJS activation failures are transient responses, and finalized effects (including fuel stops) are removed from the active map. The projection therefore exposes no durable activation failure, and a finalized Core's stop reason is unknown. A still-observable effect's `stopReason` is preserved. No history, notifications or operation policy is added.

## Inactive Core startup fuel quote (Phase 1B2.5)

Each Core's `fuel.startupQuote` carries the fitted `moduleID`, `fuelTypeID`, cached `fuelName`, `requiredQuantity`, eligible `availableQuantity`, server `sufficient` verdict, and `availability` / machine-readable `reason`. Available zero and false survive unchanged; unreadable quantities or calculation produce null and unknown. An active module has a not-applicable startup quote (`module-active`); its existing B2 effective consumption remains unchanged. Missing older-gateway quotes remain unknown. A foreign quote item ID cannot grant sufficiency.

The runtime already provides a non-mutating calculation: `moduleAttributes.getGenericModuleRuntimeAttributes`. The gateway reuses it with the fitted item, current ship/pilot, loaded charge, skill map, fitted items, active/overload contexts (excluding the quoted module's current effect), implant/system and current command-burst modifiers. This is the same generic branch used by `scene/modules.activateGenericModule` before `consumeShipModuleFuelForSession`. Industrial Core has no family-specific fuel override in the subsequent local-cycle/superweapon/banked-weapon branches. `resolveGenericModuleAttributeOverrides` / `buildLiveModuleAttributeMap` resolve the effective amount; `shipModuleFuel.roundModuleFuelQuantity` supplies the final whole-unit value. No calculation or rounding helper was extracted, and the gameplay path is unchanged.

The quote reads stacks through the existing shared fuel reader and totals them with `getFuelQuantityFromStacks`, using the same fuel-bay/cargo eligibility as `sharedFuelRuntime.consumeFuelFromShipStorage`'s `NO_FUEL` quantity gate. Sufficiency means this observed total covers the resolved amount; it does not guarantee later activation, atomic inventory writes, online/capacitor checks or other activation prerequisites will succeed. It is a current observation, without reservation, expiry, mutation, activation probe, consumption/rollback or fuel policy. WC copies the server verdict and resolves names from its existing cache.

Explicit unknown reasons include `module-state-unknown`, `core-identity-unknown`, `simulation-time-unavailable`, `module-scope-mismatch`, `fuel-calculation-unavailable`, `fuel-inventory-unavailable` and `observation-unavailable`. A readable required quantity is retained when only inventory is unavailable. Unsupported non-Core modules have not-applicable quotes. Tests execute the existing runtime calculation, modifier application, rounding and eligibility functions in an isolated VM with fixture metadata/inventory; no runtime entrypoint or real inventory writer is loaded. Set `EVEJS_CLEAN_REFERENCE` to a clean 0.12.9 source root if the default sibling reference is unavailable.

It reads existing runtime state only; no new gameplay method or write authority is added. Overnight QA composed it into mutable `EveJS-0.12.9-test`, preserving existing Upwell/Pilot Training changes. The immutable reference remains unchanged. Deployment hashes and backups are local evidence, distinct from the clean-reference manifest.

The SHA-256 manifest is [`mining-support-0.12.9-manifest.json`](../runtime-patches/mining-support-0.12.9-manifest.json). Older gateways leave the new service observations unknown. Recipient buff application/expiry and durable runtime fuel-stop history are not established by these projections. Per-compressor pairing within a shared typelist remains unavailable. Fleet access, envelope policy, positioning, effective work reach and MCC reuse are implemented below. Startup quotes do not reserve fuel or establish future action success.

## Reusable controller (Phase 2A)

`nav/miningSupportController.ts` exports the pure stateful `decideMiningSupport(services, memory, policy, relocationRequested, feedback?)` and `freshMiningSupportMemory()`. A normal caller supplies `AppFlow.readMiningSupportServices()`, retains the returned memory, and dispatches the returned `activate` / `deactivate` through its existing generic module action executor. Actions are a subset of `ScriptAction`: activation names the fitted module item ID with target zero; shutdown names the fitted item and type. This phase adds no runner registration or UI. One controller owns a pilot's support module IDs; callers must arbitrate other module controllers before dispatching.

Policy consists of `maintainBursts`, `useIndustrialCore`, `enableCompression`, and `coreRequirement` (`continueWithoutCore` / `requireCore`). Relocation is a separate input. Results contain at most one action, a correlation `actionID`, retained memory, structured issues (`reason`, severity, module ID and optional runtime code), and fitted compressor observations retaining typelist/dogma facts. States are maintaining, ready, degraded, blocked, waiting, preparing-relocation and ready-for-relocation. Degraded service results may accompany an action for another usable module. A required Core's fuel block prevents lower-priority startup; no bot/operation is stopped here.

Priority is compressor/Core settlement, desired Core prerequisite, compressor startup, then burst startup, with ascending fitted item IDs within each family. Compressor effects are settled before Core shutdown because generic manual stops may defer to cycle end, and Core finalization removes dependent modules. Disabling compression settles compressors; disabling Core settles observed Core-dependent or unknown-dependency compressors first. A policy reversal cannot cancel an outstanding stop or start services while it is settling. Active services are left alone. One active Core satisfies the desired Core prerequisite; if none is active, the first fitted Core is considered without hull/count assumptions.

Burst startup requires observed inactivity, online/cycle facts and a positive loaded charge. Unknown service/cycle state waits, while missing/empty charge reports `burst-no-charge`. Charge compatibility and activation refusals remain the generic handler's authority: the controller retains failed feedback such as `CHARGE_NOT_COMPATIBLE` as an `action-refused` issue and never selects or reloads a charge. Usable other bursts can progress deterministically. Compressor startup uses own fitted identities from the self compression projection, preserves `compressionTypeListID`, and requires a known Core dependency plus a proved active Core when that dependency is true. External facilities do not grant module authority. An active compressor with an inactive facility reports degraded service rather than claiming compression is ready. No ore compression action is emitted.

An inactive desired Core can start only with its item-matched available `startupQuote.sufficient === true`. WC never compares fuel quantities or substitutes base dogma. False or observed fuel failure produces `no-fuel`, degraded under continue-without-Core or blocked under require-Core. Continue policy maintains independent services; unknown quote/calculation remains `fuel-unknown` and waits. Missing Core reports `no-core-fitted` under the same policy. A pending stop waits for actual inactivity, regardless of ACK or elapsed boundary time.

Memory retains outstanding per-module orders and refuses duplicate requests. Matching observed active/inactive state completes an order; a correlated failed action result latches its runtime refusal until meaningful capability/quote input changes or observation proves it resolved. ACKs never complete orders. No new action is emitted from the same sample that already emitted an action; stale or unreadable samples fail closed. Eight distinct unconfirmed observations report `action-unconfirmed` as blocked without retrying or claiming completion. A proved pending Core stop continues waiting through its cycle boundary. Ship changes discard old ownership; a same-ship refit preserves outstanding orders for still-fitted matching item/type identities. Refresh observations even while waiting/blocked so later authority can settle the order.

Relocation suppresses all service startup, settles fitted compressors, requests Core shutdown, waits for actual effect removal, then requires an inactive self compression service with no active compressor identities and both movement/warp restriction gates unrestricted. The result is `ready-for-relocation`; it issues no movement and grants no other movement preconditions. Unknown capability/service state, an outstanding Core/compressor startup, or restricted/unreadable mobility prevents readiness. The separate positioning consumer below owns movement; operation policy remains a caller responsibility.

## Shared support anchor and envelope (Phase 2B1)

`GET/POST /api/bots/mining-support-anchors` owns an in-process board, without disk persistence, timers, fleet mutations or commander requirements. POST accepts `observedShipID` and `observedAtMs` (the controller observation's simulation timestamp) as guards, plus optional expected character/fleet guards described in Phase 2B2 below. Browser character/fleet/ship/range/position/policy fields cannot supply facts. The BFF binds own-fleet `GetInitState` with no fleet argument, confirms the held character in its roster, reads own space, then confirms membership again. It rejects session replacement, changed ship, unreadable membership, future/unknown sample or a read exceeding the freshness budget. Exact decimal fleet IDs never pass through an unsafe numeric conversion.

Records contain the held character, current ship item, fleet and system IDs, an opaque session epoch (never the gateway handle), simulation sample time, BFF observation/publication/expiry times, active mining-burst facts, exact compression typelist/range pairs and runtime support-effect/mobility state. Only the publisher's own service projection is shared; external facilities and legacy widest-range fields are excluded. Missing accepted runtime observations remain unknown. Effect identities are observations, not a hull/fitted-Core classifier or desired policy. A late older concurrent observation cannot overwrite a newer same-session/ship publication; roster/space system disagreement also refuses publication.

Freshness ends 10 seconds after the BFF begins the space observation, matching five nominal two-second runner ticks. Reads never renew records. Stale diagnostics remain at most 30 seconds after publication and are pruned on board access. Held-session/ship changes and removal from the fresh fleet roster mark retained records invalid immediately when detected. The board preserves separate publishers within each fleet and selects none. GET re-proves the reader's own membership and returns its short-lived roster plus records with explicit `fresh`, `stale` or `invalid` freshness, age and reason. A proven fleet with no records returns an available empty list; unreadable/unproved membership returns unknown with no anchors. Authentication/session errors still propagate normally.

`AppFlow.publishMiningSupportAnchor(observation)` is the explicit Phase 2A consumer seam. Pass the same `MiningSupportServiceSnapshot` used by `decideMiningSupport`; the flow sends only its ship/sample guards and the BFF re-reads actual service facts. Do not publish controller policy, action ACKs or a `ready` result as service authority. Call explicitly while maintaining support; stopping calls lets the lease expire. There is no automatic publisher, runner registration or UI block. `AppFlow.readMiningSupportAnchors()` uses the flow's own session token, without an MCC dependency or hidden cross-tick cache.

`resolveSupportAnchor(publication, {snapshot, receivedAtMs}, fleetRoster, nowMs)` is pure. Receipt/lease times use wall clock; simulation time is not a freshness clock. It requires fresh publication, roster and miner scene, roster membership for both pilots, a matching system and visible non-NPC ship item/pilot. Its position/radius come only from the miner's scene. Missing or mismatching identity, off-grid, stale/unknown reads and decoder geometry fallbacks fail closed. The geometry validity marker preserves the distinction between missing fields and real zero coordinates/radius without changing existing overview calculations. Corp/alliance membership supplies no fleet proof.

`supportEnvelope(resolution, requirements)` accepts a mining-burst boolean and optional exact `requireCompressionTypeListID`, without inferring resource-family labels. It conservatively intersects all required active burst ranges and matching compression ranges with `min`, returning bounded surface metres, unsatisfied, unknown or explicit unbounded when no ranged services are required. Missing/inactive matching services are unsatisfied; unreadable services or required ranges are unknown. `evaluateSupportEnvelope` uses the shared `surfaceDistanceMeters` convention (`max(0, centre distance - both hull radii)`); equality is inside. It issues no action and does not prove recipient buff application.

## Per-pilot fleet reconciliation (Phase 2B2)

`decideMiningSupportFleet(input, memory)` and `decideMiningSupportFleetMember(input, memory)` are pure reusable decisions under WC/nav. They return a structured state, issues, at most one action and its correlation ID, and updated run-local memory. They perform no IO or session acquisition. Consumers dispatch through the existing authenticated pilot's fleet actions, refresh that pilot's fleet, and feed back the action outcome with the same `{characterID, sessionEpoch}` scope and action ID. An ACK never proves membership. There is no automatic runner, coordinator, UI or second ownership registry.

`EXISTING_ONLY` is the default manual policy: use an authoritative existing fleet without creating, inviting or automatically joining. `MANAGED` allows safe create/invite/join reconciliation. `AppFlow.readMiningSupportFleet(sessionEpoch, join?)` exposes the normal loaded fleet state with its receipt time and own character identity. Refresh through the existing fleet reader first; the caller supplies an opaque run/session epoch, current own-session invite knowledge and eligible finder adverts. Omitted join facts remain unknown. Reset the epoch on session replacement. Observations older than ten seconds, future receipts, missing identity or unavailable reads fail closed. A ready fleet requires the clean `GetInitState` fleet ID and the pilot's roster row; cached session/`BoundFleet` IDs and the anchor board never prove membership.

An already-member support pilot keeps its live fleet and invites at most one eligible missing intended member, ordered by character ID. The current EveJS `inviteCharacter` gate is ordinary membership (`ensureFleetMembership`), so boss/commander rank is not required. Each invitee must have a fresh own-pilot not-in-fleet observation; missing facts wait, and an intended pilot proved in another fleet produces a conflict. No leave, kick, disband, promotion or hierarchy action exists in the controller's action vocabulary.

A fleetless support pilot first checks fresh intended-member observations for surviving fleets. One surviving fleet can be rejoined only through a matching current own-session invitation or an exact-ID eligible fleet advert. Multiple surviving fleets, or a survivor inconsistent with the run's previous fleet, require recovery. Without a usable invite/advert, surviving membership also requires recovery instead of replacement creation. Unknown or absent intended-member facts cannot prove that the previous fleet vanished. Creation requires fresh not-in-fleet evidence for every intended member (or an empty intended list), and remains pending until a new authoritative own membership read. Creation failures/ambiguous completion block rather than repeatedly creating.

The member controller requires a fresh observation of the selected support pilot's own membership. Matching fleet membership is ready; another fleet is a conflict without leaving. Direct invitations use the existing accept action. Adverts use the existing `applyToJoinFleet` protocol: its source response must prove `invited` before accept; approval-required and unknown replies do not imply an invitation. Accept still waits for a roster reread. Fleet names never select identity. Full disconnect removes membership; `reconnectCharacter` only accepts a still-existing member row and cannot restore that removal. Final-member departure can destroy the fleet, and runtime restart loses process-local fleet state; recovery therefore starts from new reads and can acquire a new fleet ID.

Memory is volatile and scoped to one pilot/run/session. It suppresses another mutation from the same or older own receipt. Invite requests have a 30-second pending/cooldown window and at most three acknowledged attempts per missing member/fleet; a retry additionally requires fresh member absence and known invite state. A present matching invite suppresses another invite. Unknown, pending or refused outcomes never trigger automatic invite retries; joining the fleet clears that member's pending record. Accept retries require a newly received matching invitation plus cooldown and use the existing join watcher's three-attempt bound. Advert application is not repeatedly retried on ambiguous replies. Late feedback from another pilot/epoch or action ID is ignored.

`AppFlow.publishReconciledMiningSupportAnchor(fleetResult, serviceObservation)` requires freshly observed support membership and the current loaded own-ship service sample. It sends ship/sample guards plus optional expected character/fleet guards to the existing board route. These expected values can only reject a mismatch; they cannot choose the authenticated pilot or supply fleet/service facts. The BFF re-reads its held pilot's actual fleet before and after a fresh space read and derives the publication identity and services itself. Recreation therefore publishes under the newly reread fleet ID. Prior-fleet records cannot satisfy a new-fleet reader and retain the existing expiry/invalidation behavior. The older explicit publisher remains compatible and still independently proves live membership on the server.

Unadvertised surviving fleets without a valid invitation, approval-based adverts without a subsequent invitation, unavailable member facts, refused actions and ambiguous mutations remain structured waiting/blocked/recovery cases. A future caller may present them to user policy; this phase adds no gameplay authority, runtime patch, movement, support positioning, mining, tractor/collection or operation-specific coordinator.

## Fleet Miner

The separate `fleet-mine` script block selects a support pilot and mines the current visible grid outside an operation. It does not replace the classic belt/site block or tour arbitrary belts when resources or support are unavailable. In an operation it reuses the shared exact-target, travel and depletion path. The normal flow reads a fresh own fleet, anchor board, scene and fitted mining identities. A joined reader's actual board roster may confirm `EXISTING_ONLY` membership through the member reconciler; it is not converted into a fictitious support pilot's `GetInitState`, and cannot discover/join a fleet while the reader is fleetless.

`decideFleetMinerGeometry` resolves the selected anchor in the miner's scene, intersects its required service envelope with every online miner's exact effective reach, and selects a compatible visible resource. Current feasible work wins over movement; ties prefer the working target, smaller movement and stable identity. Two measured balls define a deterministic bounded destination including hull/resource radii. Missing range, stale authority, off-grid support and no feasible intersection expose `UNKNOWN`, `SUPPORT_UNAVAILABLE` or `REPOSITION_NEEDED`. There is no 10 km fallback, hull branch, orbit order or invented off-grid coordinate.

The script adapter settles existing miner modules and positively returns controlled drones before adopting/changing work or moving. It checks actual movement permission, observes the issued movement and brakes within both constraints before reusing the existing lock/activate loop. Support loss or an impossible intersection also brakes a previous movement after settlement. ACK does not prove arrival; unobserved movement retries are bounded. Freshness starts when the scene's own request resolves, before unrelated reads finish. The accepted mining/defensive drone wrapper, terminal return proof, shared travel ownership and classic block behavior remain in place.

## Reusable positioning

`decideSupportPositioning` owns one run-local movement memory and the accepted 2A service memory. It accepts fresh own scene/service measurements, the current authoritative fleet roster, intended character IDs and the observed support envelope. It resolves each intended recipient from exactly one visible player ship in that roster; off-grid, missing, duplicate, stale or invalid geometry waits. The bounded deterministic policy considers a centroid, medoids, pair midpoints and 96 farthest-recipient steps, for at most 32 recipients. Pair separation can prove `UNSATISFIED`; an inconclusive candidate search returns `WAIT`, without claiming global optimality. Already covered recipients hold, including the boundary deadband.

Relocation captures the last proved range before services disappear during shutdown. Dependent mining/tractor activity and owned drone flight must be confirmed settled before 2A settles compressors/Core. Only `ready-for-relocation` permits one existing `CmdGotoPoint` action. The BFF validates finite numeric coordinates and rereads the expected ship and system before dispatch. ACK cannot prove arrival: a subsequent scene must geometrically reach the latched point, receive one stop order and then report measured settled velocity with `STOP` mode while recipients remain covered. Braking may carry the ship outside the narrow target-point window; final envelope coverage must still be measured. Only then is relocation cleared and service maintenance allowed. Movement refusal/ambiguity, two minutes without measured progress, or ten minutes total unconfirmed travel latch `BLOCKED`. Progress requires a newer coherent scene and at least one metre less distance; repeated reads or reverse movement do not renew it. Ship, fitting, fleet, system or session epoch changes discard old targets and feedback.

`AppFlow.tickMiningSupportPositioning(memory, request)` is the explicit normal WC adapter: one call refreshes fit/dogma, own fleet and a coherent scene/drone observation, decides, dispatches at most one action with this pilot's token and returns correlated feedback for the next tick. The caller owns cadence and one memory per run. It rejects concurrent ticks and other running/paused ship controllers; no automatic background loop or MCC configuration is implied. No new movement runtime or hull whitelist is introduced.

The compression projection also handles a fresh runtime entity whose facility cache remains undefined: a readable active-effect map containing no compressor proves inactive. Missing effect authority or an active compressor without actual typelist facts remains unknown; the projection never initialises runtime state. Braking has a separate two-minute observation deadline. Residual warp-arrival velocity also requires actual braking before Core activation; a STOP label alone is insufficient.

Fresh comfortable coverage may supersede a latched minimax destination when
recipients return during Core shutdown. After dependent/service settlement and
actual mobility, an already stopped support clears that obsolete trip; a moving
support brakes first. Deadband coverage alone never proves measured STOP.

Compressor shutdown uses the already projected generic effect lifecycle, matched by fitted module item/type and compression effect identity. A source-observed deferred stop before its simulation-time boundary does not consume the controller's uncertainty-poll budget. After that boundary a retained effect remains pending and bounded unconfirmed polls can block; elapsed time and ACK never prove inactivity. Actual effect removal permits Core shutdown.

## Item-scoped mining and tractor reach

The cumulative 0.12.9 artifact also exposes own-ship `moduleReach`. Mining reach delegates to the same `buildEntityMiningSnapshot` used by activation, including the actual fitted item, loaded charge, skills, active effects, implants, burst and system modifiers. Tractor reach and activation share `readTractorBeamModuleSnapshot` with unchanged runtime rounding and context. The tractor settlement surface distance comes from the existing runtime constant. These readers perform no target probes, inventory writes or module actions. The activation gate's one-metre tolerance is not added to observed range.

`readObservedModuleReach(scene, moduleID, typeID)` requires the exact own ship, module item/type and simulation sample. Missing or malformed observations remain unavailable; callers must refresh rather than substitute fitting base range or a guessed mining distance. A measured zero remains zero. Online state, target compatibility, loot rights, actual geometry and other activation preconditions remain separate caller gates. The patch is cumulative against immutable clean 0.12.9; deployment must compose its gateway changes into the current mutable runtime and preserve unrelated patches.

## Optional support self-mining

`decideSupportSelfMining` is a stationary adapter over `decideMiningAction` and the accepted mining/combat drone flight controller. It filters only mineable rows, retaining hostile/safety facts. Turret candidates require all requested online fitted module item/type reaches from the same scene, matching resource family and effective lock range. Drone mining uses the existing resolved command leash, which is not a claim about drone optimal range or yield. Runtime still owns final charge/target compatibility and activation refusal. Unknown reach grants no productive action. There is no hull-name policy.

The normal `tickMiningSupportPositioning` adapter accepts an optional `selfMining` request containing caller-owned memory, a real MiningPlan and enabled/stop flags. Emergency/Stop/failed-work cleanup preempts maintenance; otherwise support actions outrank optional mining. Only measured stopped motion, HOLD, no relocation and acceptable support state allow work. One tick dispatches at most one normal action through the current pilot token; drone launch reuses `wholeStackLaunch`. Running mining modules and every controlled drone must positively settle before relocation. Malformed controlled-flight rows cannot decode into an empty-flight proof.

Full holds, health escape, no reachable resource and other classic travel/unload decisions settle first and return a caller handoff. Target changes settle the old work before reselecting. The adapter emits no movement, dock, unload, fleet or support-module action. An unresolved productive action can block final handoff while permitting cleanup of other known activity; ACK never proves completion. Action IDs remain monotonic across same-scope plan changes. Memory remains run-local and resets on pilot/session/ship/fit/fleet/system changes; a blocked fault or terminal handoff requires explicit caller recovery. This phase adds no autonomous MCC runner or configuration.

## Sequential support tractor

`decideSupportTractor` owns one fitted beam and one existing BFF container lease. Its caller supplies bounded container IDs with operation/test creation provenance and allowed owners; overview membership alone never grants eligibility. Selection uses the fresh item/type-scoped tractor reach, online/cycle facts and surface geometry. It acquires the claim before locking/activation, renews it during work and keeps it on unknown/refused results. Fresh GetAllInfo active-effect environments, matched to own character/ship/module/type and the scene's tractor effect identity, prove the exact selected target. Missing or disagreeing observations wait or block; no lock or ACK substitutes for that proof.

The optional `tractor` request on the normal support tick shares the existing movement owner. Support actions and safety cleanup take priority; due lease maintenance precedes optional self-mining. Relocation stops beams before Core settlement or movement. Unknown/lost target eligibility stops known beam activity while retaining the claim. Other active tractors prevent a second pull. Settlement uses the runtime-projected follow distance and measured target velocity; millimetre geometry quantisation handles floating-point roundoff at large system coordinates without adopting the activation gate's one-metre tolerance. Actual beam inactivity is required before release. Tractor-only never transfers cargo or reports a container emptied, and serviced IDs are bounded per run.

Collection may request a retained settled lease and receives `readyContainerID`; the subsequent collection owner must supply its actual source-empty proof before release. Refused/ambiguous actions latch a structured fault while allowing known beam cleanup, retaining diagnostics and lease for explicit recovery. A scope/run change with unresolved ownership blocks and preserves the old memory rather than silently handing its target to another run. The adapter emits at most one normal action per tick, with no movement runtime or hull policy.

Active-ship loaded charges may carry `(shipID, slotFlagID, typeID)` tuple identities. Fitting preserves and validates these rather than fabricating a numeric inventory ID; burst startup accepts the item-matched tuple and positive observed quantity.

## Optional ore collection

The normal support tick accepts `collection` with caller-owned memory and two explicit policies: `TRACTOR_ONLY` and `TRACTOR_AND_COLLECT`. Collection requires the sequential tractor's settled positive lease. It reads the source and caller-owned bays, routes only known category-25 resource stacks through `bayRouting`, and dispatches at most one measured transfer or compression action per tick. Fuel, ammunition and other source contents remain untouched. A present specialised hold never spills ore into cargo when full. Missing capacity, volume, classification or inventory rows reports `UNKNOWN`; measured no-fit reports `FULL`. Full collection does not block ordinary support maintenance.

Strict automation decoders keep malformed/dropped/duplicate rows and incomplete capacities unknown. Transfer settlement requires the exact source quantity loss and a matching owned-hold gain, including splits, merged stacks and reminted item identities. API success alone proves nothing. Partial or ambiguous changes retain pending memory and claim, suppress new work, and require observation or explicit recovery. Stop may settle the beam while the unresolved inventory result keeps its lease. A scope change preserves unresolved memory. Inventory writes additionally guard expected own ship/system at the BFF; fresh scene/fleet/fitting checks surround asynchronous reads.

Collected provenance records exact scope, bay, item, type and quantity. Only a new fully collected stack, or a measured extension of an already fully collected stack, may be compressed. A merge into preexisting ore remains collected but is ineligible for whole-stack compression. Unobserved quantity changes invalidate provenance. `/api/mining/compression-compatibility` reads the configured EveJS `clientTypeLists` and `reprocessingStatic` reference tables, applying their inclusion/exclusion rules and source/output recipe. It is static compatibility only; fresh own active typelist/range observations and the runtime handler still govern availability. Missing data stays unknown. Compression requires the exact six-value response tuple plus fresh source/output hold transformation, including same-item-ID type replacement. No remote miner inventory is read or mutated.

`sourceEmpty` is a strict proof of the whole source being empty. Ore exhaustion in a mixed container never produces that proof or an emptied mark. The caller can pass the proved container ID to the tractor for safe release, or request normal settlement/handoff. There is no automatic unloading, destruction, generic cargo sweep or second logistics engine.

Scene and module-reach authority now share one captured finite numeric simulation timestamp; missing clocks are not coerced to zero. This removes intermittent false incoherence while retaining fail-closed decoder matching.
