# Mining Support contracts and current implementation

`AppFlow.readMiningSupportServices()` enriches Phase 1A capabilities with the latest successful, same-ship space snapshot. It performs no IO, actions, fitting loads or caching. Callers refresh through the existing `loadSpaceSnapshot()` reader. A failed read, ship change, absent field or unreadable observation grants no service facts. The server sample timestamp is retained; no freshness timer or recipient-expiry claim is introduced.

Each fitted Mining Foreman Burst has a separate active/inactive/unknown service state. Active facts preserve the runtime module item ID and type, effect identity, charge type, computed burst range, cycle and buff durations, and buff-collection IDs/values. These are the activation snapshot produced by `commandBurstRuntime`, not a new calculation. The current runtime effect state does not retain the consumed charge item's ID, so the service's charge item ID remains null; the capability snapshot independently retains the latest observed loaded charge.

Compression service records preserve facility ship/pilot/owner identity, self/external origin, active/inactive/unknown state, active compressor identities when available, and each exact `{typeListID, rangeMeters}` association from `compressionFacilityTypelists`. External does not prove fleet membership or access. Typelist IDs are retained without guessing ore/ice/gas labels. The authority currently merges compressors covering the same typelist; module identities are therefore listed independently without inventing a module-to-pair association. The old `compressionFacility.rangeMeters` maximum remains for compatibility with existing WC consumers and is never used to construct these new service facts.

Each fitted Industrial Core has an independent inactive/active/deactivation-pending/unknown observation, matched by fitted item and type identity. Current effect identity, start, cycle duration, next boundary, stop request and scheduled deactivation timestamps are preserved. A passed boundary never proves shutdown while the authoritative active effect remains. Only actual effect-map absence proves current inactivity; no completed shutdown timestamp or reason is fabricated.

Movement and warp restrictions are separate verdicts from `shipActionRestrictions.isShipMovementLockedByRuntime` and `isShipWarpDisabledByRuntime`, evaluated using the scene simulation-clock reader used by the handlers. Zero is a valid clock reading; unavailable simulation time grants no verdict. These are the same runtime gates enforced by pilot movement/warp handlers, and they can disagree. The scope is explicitly `runtime-action-restrictions`: unrestricted is not a guarantee that target validity, current warp/landing, docking, tackle, destination or other action preconditions pass. Known restricting module/effect identities accompany the verdict; non-module restrictions may have no effect attribution. The warp gate's existing `SHIP_IMMOBILE` code is retained; sublight handlers do not supply a code. An unreadable gate stays unknown.

Core fuel requirements come from the existing runtime module authority. Fuel name is resolved only from WC's existing names cache. While active, `effectivePerActivation` is copied from the effect's already-rounded `fuelPerActivation`, the exact value passed to the continuing-cycle consumer. While inactive it remains null: base consumption is not presented as an effective activation quote. Eligible inventory stacks, location/flag identities and available quantity use `sharedFuelRuntime.getFuelStacksForShipStorage` / `getFuelQuantityFromStacks` and `fuelBayInventory.getFuelStorageFlagsForType`. No additional WC inventory loader, fuel bay router, rounding or skill arithmetic is introduced. A readable empty inventory is zero; failed or identity-unscoped inventory reads are unknown.

The decoder retains supplied activation failure and stop codes and normalizes `NO_FUEL` / `fuel` without deriving them from inventory quantity or inactivity. Current EveJS activation failures are transient responses, and finalized effects (including fuel stops) are removed from the active map. The projection therefore exposes no durable activation failure, and a finalized Core's stop reason is unknown. A still-observable effect's `stopReason` is preserved. No history, notifications or operation policy is added.

## Inactive Core startup fuel quote (Phase 1B2.5)

Each Core's `fuel.startupQuote` carries the fitted `moduleID`, `fuelTypeID`, cached `fuelName`, `requiredQuantity`, eligible `availableQuantity`, server `sufficient` verdict, and `availability` / machine-readable `reason`. Available zero and false survive unchanged; unreadable quantities or calculation produce null and unknown. An active module has a not-applicable startup quote (`module-active`); its existing B2 effective consumption remains unchanged. Missing older-gateway quotes remain unknown. A foreign quote item ID cannot grant sufficiency.

The runtime already provides a non-mutating calculation: `moduleAttributes.getGenericModuleRuntimeAttributes`. The gateway reuses it with the fitted item, current ship/pilot, loaded charge, skill map, fitted items, active/overload contexts (excluding the quoted module's current effect), implant/system and current command-burst modifiers. This is the same generic branch used by `scene/modules.activateGenericModule` before `consumeShipModuleFuelForSession`. Industrial Core has no family-specific fuel override in the subsequent local-cycle/superweapon/banked-weapon branches. `resolveGenericModuleAttributeOverrides` / `buildLiveModuleAttributeMap` resolve the effective amount; `shipModuleFuel.roundModuleFuelQuantity` supplies the final whole-unit value. No calculation or rounding helper was extracted, and the gameplay path is unchanged.

The quote reads stacks through the existing shared fuel reader and totals them with `getFuelQuantityFromStacks`, using the same fuel-bay/cargo eligibility as `sharedFuelRuntime.consumeFuelFromShipStorage`'s `NO_FUEL` quantity gate. Sufficiency means this observed total covers the resolved amount; it does not guarantee later activation, atomic inventory writes, online/capacitor checks or other activation prerequisites will succeed. It is a current observation, without reservation, expiry, mutation, activation probe, consumption/rollback or fuel policy. WC copies the server verdict and resolves names from its existing cache.

Explicit unknown reasons include `module-state-unknown`, `core-identity-unknown`, `simulation-time-unavailable`, `module-scope-mismatch`, `fuel-calculation-unavailable`, `fuel-inventory-unavailable` and `observation-unavailable`. A readable required quantity is retained when only inventory is unavailable. Unsupported non-Core modules have not-applicable quotes. Tests execute the existing runtime calculation, modifier application, rounding and eligibility functions in an isolated VM with fixture metadata/inventory; no runtime entrypoint or real inventory writer is loaded. Set `EVEJS_CLEAN_REFERENCE` to a clean 0.12.9 source root if the default sibling reference is unavailable.

## EveJS 0.12.9 transport extension

The additive gateway patch supplies `ship.miningBurstServices`, `ship.compressionService`, `ship.coreMobilityFuel`, own pilot/owner identity, and ship-entity `compressionService` through the existing space snapshot route. It reads existing runtime state only; no new gameplay method or write authority is added. Overnight QA composed it into mutable `EveJS-0.12.9-test`, preserving existing Upwell/Pilot Training changes. The immutable reference remains unchanged. Deployment hashes and backups are local evidence, distinct from the clean-reference manifest.

The SHA-256 manifest is [`mining-support-0.12.9-manifest.json`](../runtime-patches/mining-support-0.12.9-manifest.json). The package is cumulative: Phase 1B1 + Phase 1B2 + Phase 1B2.5 apply directly to clean immutable 0.12.9, without first applying earlier support patches. For a separately authorized deployment, install its complete [`miningSupportProjection.js`](../runtime-patches/miningSupportProjection.js) payload at the stated destination and apply [`mining-support-services.patch`](../runtime-patches/mining-support-services.patch). Check the patch from the clean immutable EveJS 0.12.9 root with `git apply --check /path/to/wc/runtime-patches/mining-support-services.patch`; never modify that reference. These additions occupy separate gateway seams from the existing Upwell and Pilot Training patches.

Older gateways leave the new service observations unknown. Recipient buff application/expiry and durable runtime fuel-stop history are not established by these projections. Per-compressor pairing within a shared typelist remains unavailable. Fleet access, envelope policy, positioning, effective work reach and MCC reuse are implemented below. Startup quotes do not reserve fuel or establish future action success.

## Item-scoped mining and tractor reach

The cumulative 0.12.9 artifact also exposes own-ship `moduleReach`. Mining reach delegates to the same `buildEntityMiningSnapshot` used by activation, including the actual fitted item, loaded charge, skills, active effects, implants, burst and system modifiers. Tractor reach and activation share `readTractorBeamModuleSnapshot` with unchanged runtime rounding and context. The tractor settlement surface distance comes from the existing runtime constant. These readers perform no target probes, inventory writes or module actions. The activation gate's one-metre tolerance is not added to observed range.

`readObservedModuleReach(scene, moduleID, typeID)` requires the exact own ship, module item/type and simulation sample. Missing or malformed observations remain unavailable; callers must refresh rather than substitute fitting base range or a guessed mining distance. A measured zero remains zero. Online state, target compatibility, loot rights, actual geometry and other activation preconditions remain separate caller gates. The patch is cumulative against immutable clean 0.12.9; deployment must compose its gateway changes into the current mutable runtime and preserve unrelated patches.
